# ТЗ для одногрупників: зробити БД для PC-NEST

## 0) Мета простими словами
Потрібно підготувати базу даних так, щоб сайт стабільно працював: користувачі, компоненти, збірки, зв'язки між ними, міграції, тестові дані.

## 1) Де працюємо
- Основна гілка: `dev`
- Кожен (або пара) створює окрему гілку від `dev`.
- Формат назви гілки: `feature/db-<name>`

Приклад:
```bash
git checkout dev
git pull
git checkout -b feature/db-andrii
```

## 2) Що треба зробити (обов'язково)

### 2.1 Підключити PostgreSQL
В `.env` мають працювати параметри:
- `DB_ENGINE=postgresql`
- `DB_NAME`
- `DB_USER`
- `DB_PASSWORD`
- `DB_HOST`
- `DB_PORT`

Перевірка: `python manage.py migrate` виконується без помилок.

### 2.2 Перевірити моделі
У проєкті мають бути коректні моделі:
- `User` (роль `user/admin`)
- `Component`
- `ComponentSpec` (1:1 з `Component`)
- `Build`
- `BuildComponent` (M:N між `Build` і `Component`)

Що перевірити:
- правильні типи полів
- `ForeignKey`, `OneToOne`, `ManyToMany through`
- `unique_together` для `BuildComponent (build, component)`

### 2.3 Міграції
- Переконатись, що міграції створені та актуальні.
- Якщо змінили моделі: зробити нову міграцію.

Команди:
```bash
python manage.py makemigrations
python manage.py migrate
```

### 2.4 Початкові тестові дані
Потрібно, щоб після запуску були дані для перевірки:
- хоча б 2 користувачі (`admin`, `demo`)
- хоча б 8 компонентів різних типів
- хоча б 1 готова збірка

Варіант реалізації:
- або management command (`seed_demo_data`)
- або fixtures

## 3) Додатково (бажано)
- Індекси для полів, по яких часто фільтруємо:
- `Component.type`
- `Component.brand`
- `Component.price`
- Продумати `on_delete` (щоб видалення не ламало дані)
- Перевірити, що не створюються дублікати компонентів у тій самій збірці

## 4) Що здати в Pull Request
У PR повинно бути:
- змінені/додані файли моделей (якщо були зміни)
- файли міграцій
- оновлений `.env.example` (якщо додали нові змінні)
- короткий опис, що зроблено
- як запускати та перевіряти

Шаблон опису PR:
1. Що змінено
2. Чому це потрібно
3. Як перевірити локально
4. Ризики/обмеження

## 5) Як перевірити перед пушем
Запустити послідовно:
```bash
python manage.py check
python manage.py migrate
python manage.py seed_demo_data
python manage.py runserver
```

Перевірити вручну:
- Реєстрація/логін працюють
- Каталог відкривається
- Можна створити збірку
- Працює перевірка сумісності
- Дані реально записуються в БД

## 6) Критерії "готово"
Задача вважається завершеною, якщо:
- PostgreSQL підключається і міграції проходять
- Моделі відповідають ТЗ
- Є тестові дані
- Сайт працює без падінь на основних сторінках
- PR пройшов review

## 7) Після цього
- Відкриваєте PR у `dev`
- Після перевірки робимо merge
- Далі переходимо до наступного блоку (UI/логіка/API)
