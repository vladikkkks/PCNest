# Звіт з аналізу проєкту PC-NEST та бази даних

## 1. Загальна характеристика проєкту

PC-NEST — це вебзастосунок на Django для підбору комплектуючих ПК, перегляду каталогу компонентів, створення власних збірок та перевірки їх сумісності. З точки зору бази даних проєкт охоплює:

- зберігання користувачів і ролей;
- зберігання каталогу комплектуючих;
- зберігання розширених технічних характеристик компонентів;
- зберігання користувацьких збірок;
- зберігання зв’язків між збірками та компонентами;
- підтримку тестового наповнення БД демонстраційними даними.

Під час аналізу було досліджено:

- налаштування підключення до БД;
- Django-моделі та міграції;
- SQL-структуру локальної бази `db.sqlite3`;
- логіку взаємодії застосунку з БД у `views`, `forms`, `admin` і management commands;
- фактичний вміст таблиць у наявній локальній БД.

## 2. Технології та спосіб підключення БД

У проєкті використовується Django ORM, яка є основним шаром доступу до даних. Конфігурація БД побудована гнучко:

- за замовчуванням у `config/settings.py` проєкт орієнтований на `PostgreSQL`;
- для локальної роботи передбачено переключення на `SQLite` через змінну `DB_ENGINE=sqlite`;
- у репозиторії є готовий SQL-скрипт `db/init_postgres.sql` для створення бази `pc_nest` і користувача `pc_nest_user`;
- у корені проєкту вже присутня локальна база `db.sqlite3`, яку використано для фактичного аналізу структури та даних.

Таким чином, архітектура БД є подвійною:

- `PostgreSQL` задумана як основна серверна СУБД;
- `SQLite` використовується як проста локальна база для розробки, демонстрації та тестування.

## 3. Логічна модель даних

Основу предметної області формують 5 власних сутностей.

### 3.1. `User`

Користувач реалізований через кастомну модель `User`, яка наслідує `AbstractUser`. До стандартних полів Django додано поле:

- `role` — роль користувача: `user` або `admin`.

Ця таблиця використовується для:

- реєстрації та авторизації;
- розмежування доступу;
- прив’язки збірок до конкретного користувача.

### 3.2. `Component`

Таблиця компонентів є центральною для каталогу. Вона містить:

- назву компонента;
- тип компонента;
- бренд;
- ціну;
- зображення;
- параметри сумісності: `socket`, `ram_type`, `wattage`;
- опис;
- дату створення запису.

Типи компонентів задаються через `TextChoices` і охоплюють:

- CPU;
- motherboard;
- RAM;
- GPU;
- PSU;
- storage;
- case;
- cooler.

Тобто одна таблиця `Component` універсально зберігає всі категорії комплектуючих.

### 3.3. `ComponentSpec`

Таблиця `ComponentSpec` розширює запис про компонент за схемою `1:1`. Вона містить:

- `manufacturer`;
- `release_year`;
- `warranty`;
- `extra` у форматі `JSON`.

Це правильне рішення з погляду нормалізації: базові характеристики винесені в основну таблицю `Component`, а додаткові технічні параметри зберігаються окремо.

Особливо важливо, що поле `extra` реалізоване як `JSONField`, тобто дозволяє зберігати довільні характеристики різних типів компонентів без створення великої кількості спеціалізованих колонок.

### 3.4. `Build`

Таблиця збірок описує користувацькі конфігурації ПК. Вона містить:

- власника збірки (`user`);
- назву;
- унікальний `slug` на основі UUID;
- дату створення;
- дату оновлення.

Окремо в моделі реалізовані бізнес-методи:

- `get_total_price()` — обчислення загальної вартості збірки;
- `get_share_url()` — формування URL для поширення;
- `check_compatibility()` — перевірка сумісності компонентів.

### 3.5. `BuildComponent`

Це проміжна таблиця для реалізації зв’язку `M:N` між `Build` і `Component`.

Вона містить:

- посилання на збірку;
- посилання на компонент;
- дату додавання компонента.

Для неї визначено обмеження `unique_together(build, component)`, яке не дозволяє додати один і той самий компонент двічі до тієї самої збірки.

## 4. Зв’язки між таблицями

У проєкті реалізовано такі зв’язки:

- `User 1:N Build` — один користувач може мати багато збірок;
- `Component 1:1 ComponentSpec` — один компонент має одну розширену специфікацію;
- `Build M:N Component` через `BuildComponent` — одна збірка містить багато компонентів, а один компонент може входити до багатьох збірок.

Із погляду проєктування це вдала схема, тому що:

- користувачі відокремлені від предметних сутностей;
- специфікації не перевантажують основну таблицю компонентів;
- зв’язок збірок і компонентів винесений у окрему таблицю, що відповідає правилам реляційного моделювання.

## 5. Фізична структура локальної БД `SQLite`

На момент аналізу в `db.sqlite3` наявні як власні таблиці проєкту, так і службові таблиці Django.

### 5.1. Власні таблиці проєкту

- `accounts_user`
- `catalog_component`
- `catalog_componentspec`
- `builds_build`
- `builds_buildcomponent`

### 5.2. Службові таблиці Django

- `auth_group`
- `auth_group_permissions`
- `auth_permission`
- `django_admin_log`
- `django_content_type`
- `django_migrations`
- `django_session`
- а також проміжні таблиці для груп і дозволів користувачів.

### 5.3. Ключі та обмеження

У фактичній структурі бази є:

- первинні ключі `id` для всіх основних таблиць;
- `UNIQUE` для `accounts_user.username`;
- `UNIQUE` для `builds_build.slug`;
- `UNIQUE` для `catalog_componentspec.component_id`, що гарантує зв’язок `1:1`;
- складений `UNIQUE` для `builds_buildcomponent(build_id, component_id)`.

Додатково `SQLite` зберігає зовнішні ключі між таблицями:

- `builds_build.user_id -> accounts_user.id`;
- `builds_buildcomponent.build_id -> builds_build.id`;
- `builds_buildcomponent.component_id -> catalog_component.id`;
- `catalog_componentspec.component_id -> catalog_component.id`.

## 7. Як працює база даних у самому застосунку

### 7.1. Отримання даних для каталогу

У каталозі використовується ORM-запит:

- `Component.objects.select_related('spec').all()`

Далі до нього застосовуються:

- фільтрація за типом;
- фільтрація за брендом;
- фільтрація за діапазоном ціни;
- пошук за назвою і брендом;
- сортування;
- пагінація.

Це означає, що БД виконує не просто зберігання, а активну підтримку вибірок для користувацького інтерфейсу.

### 7.2. Отримання деталей компонента

Сторінка компонента використовує `select_related('spec')`, завдяки чому основний запис і специфікація підтягуються одним логічним зверненням без зайвих повторних запитів.

### 7.3. Створення збірки

Під час створення збірки відбувається така послідовність:

1. З форми надходять назва збірки та список ID компонентів.
2. Створюється запис у `Build`.
3. Для кожного вибраного компонента створюється запис у `BuildComponent`.
4. Після збереження викликається `check_compatibility()`.

Таким чином, БД забезпечує:

- збереження власника збірки;
- збереження складу збірки;
- можливість подальшого розрахунку ціни та сумісності.

### 7.4. Перевірка сумісності

Перевірка сумісності працює на рівні бізнес-логіки Django-моделі `Build`, але базується на даних, що лежать у БД. Перевіряються:

- сумісність сокета між CPU і материнською платою;
- сумісність типу пам’яті RAM і материнської плати;
- достатність потужності блока живлення відносно сумарного споживання інших компонентів.

Тобто база даних зберігає параметри, а модель на їх основі виконує логічний аналіз.

### 7.5. Додавання і видалення компонентів зі збірки

Для AJAX-операцій використовуються:

- `BuildComponent.objects.get_or_create(...)` — додавання;
- `BuildComponent.objects.filter(...).delete()` — видалення.

Завдяки `get_or_create()` і `unique_together` система уникає дублювання однакових компонентів у межах однієї збірки.

### 7.6. Профіль користувача

У профілі користувача запитуються всі його збірки з попереднім завантаженням пов’язаних компонентів:

- `prefetch_related('build_components__component')`

Це зменшує кількість окремих звернень до БД і робить роботу сторінки ефективнішою.

### 7.7. Адміністрування компонентів

Адміністратор може:

- створювати компонент;
- створювати або редагувати його специфікацію;
- редагувати компонент;
- видаляти компонент.

Тобто БД підтримує повний цикл CRUD-операцій для довідника комплектуючих.

## 8. Наповнення бази тестовими даними

Для БД у проєкті передбачено два сценарії заповнення.

### 8.1. `seed_demo_data`

Команда створює:

- користувача `admin`;
- користувача `demo`;
- 8 компонентів різних типів;
- специфікації для кожного компонента;
- одну готову демонстраційну збірку.

Перевага цієї команди полягає в тому, що вона використовує:

- `get_or_create()`;
- `update_or_create()`.

Завдяки цьому її можна запускати повторно без масового створення дублікатів.

### 8.2. `seed_large_demo_data`

Друга команда призначена для генерації більшого набору тестових даних:

- багато компонентів;
- багато збірок;
- випадкові характеристики;
- можливість очистки попередніх згенерованих демоданих.

Це корисно для перевірки навантаження, роботи фільтрів і поведінки каталогу на більш реалістичному обсязі записів.

## 9. Позитивні сторони реалізації БД

Після аналізу можна виділити такі сильні сторони:

- структура БД відповідає предметній області;
- правильно реалізовані зв’язки `1:N`, `1:1` і `M:N`;
- використовується кастомна модель користувача, що дає гнучкість;
- специфікації компонентів винесені в окрему таблицю;
- `JSONField` робить схему гнучкою для різних типів технічних характеристик;
- є міграції для всіх основних сутностей;
- реалізовано тестове наповнення БД;
- застосунок вже використовує `select_related` і `prefetch_related` для оптимізації доступу до даних;
- є обмеження унікальності для запобігання дублюванню.

## 10. Виявлені обмеження та рекомендації

Під час аналізу також виявлено моменти, які можна покращити.

### 10.1. Відсутність явних індексів на часто фільтрованих полях

У технічному завданні згадувалась бажаність індексів для:

- `Component.type`;
- `Component.brand`;
- `Component.price`.

У поточних моделях окремі індекси для цих полів явно не задані. На невеликому обсязі даних це не критично, але при рості каталогу може вплинути на швидкість фільтрації та сортування.

Рекомендація: додати `db_index=True` або `indexes` у `Meta` для цих полів.

### 10.2. Частина правил цілісності реалізована на рівні ORM, а не БД

Перевірка сумісності компонентів виконується не в самій СУБД, а в Python-коді моделі `Build`. Це нормальне рішення для бізнес-логіки, але означає, що:

- БД не контролює сумісність самостійно;
- перевірка спрацьовує лише тоді, коли код застосунку викликає відповідний метод.

Рекомендація: у звіті для практики варто підкреслити, що БД зберігає параметри сумісності, а логіка їх перевірки винесена в прикладний рівень.

### 10.3. Не перевірено виконання Django-команд у поточному середовищі

Під час аналізу локальне середовище не мало встановлених Python-залежностей із `requirements.txt`, тому `python manage.py check` не виконався через відсутність `Django`.

Це не завадило аналізу коду і файлу `db.sqlite3`, але означає, що:

- структура була перевірена статично;
- фактичний запуск застосунку в цьому середовищі не підтверджено.

### 10.4. Вибір між PostgreSQL і SQLite треба чітко пояснити

У проєкті є дві конфігурації БД:

- цільова — `PostgreSQL`;
- локальна/демонстраційна — `SQLite`.

Для звіту це слід подати не як суперечність, а як свідоме рішення:

- `PostgreSQL` краще підходить для основного розгортання;
- `SQLite` спрощує локальну розробку та демонстрацію.

## 11. Висновок

У результаті аналізу встановлено, що в проєкті PC-NEST база даних реалізована логічно й достатньо якісно для навчального вебзастосунку. Вона охоплює всі ключові сутності предметної області: користувачів, компоненти, специфікації, збірки та зв’язки між ними.

Найважливіше з точки зору обов’язків, пов’язаних із БД:

- спроєктовано структуру таблиць і зв’язків;
- реалізовано міграції;
- налаштовано підтримку PostgreSQL і SQLite;
- забезпечено тестове наповнення бази;
- додано механізми захисту від дублікатів;
- використано ORM-оптимізації для читання даних;
- закладено основу для перевірки сумісності компонентів на основі даних БД.

Отже, роботу з базою даних у цьому проєкті можна оцінити як завершену на хорошому рівні для практичного навчального завдання, із кількома зрозумілими напрямами для подальшого вдосконалення.
